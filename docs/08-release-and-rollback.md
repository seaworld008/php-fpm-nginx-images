# 8. 发布、回滚与交付标准

## 8.1 发布前必须具备

- 可重建源码、完整锁、可信下载/补丁签名证据和许可说明。
- PHP 完整供应商修订、Nginx 版本、扩展、架构与依赖清单。
- 每个 CVE 的独立状态与限制；来源不完整不能写已修复。
- 制品 SHA256/SBOM/构建日志；镜像同时记录 manifest digest，不能混淆 config ID 和 docker save 归档 hash。
- 实际 CLI/FPM、扩展、业务、生命周期、性能和回滚结果；未测试照实列出。
- 没有业务密钥或生产信息；推送制品、公开发布和生产部署分别获得授权。

正式版本的锁不能包含 null、假 hash、省略号或 latest。建议标签包含 php72、平台、供应商修订和发布序号；镜像部署优先 digest。没有原生平台验证不能发布“多架构已支持”。

## 8.2 候选与正式制品

当前仓库只提供文档和工具，没有正式镜像/二进制。未来 `candidate` 不能冒充 `fixed`；最小回移应明确标识和风险接受，不把扫描误报整体静默。

对商业包/补丁先审核再分发权限，不得把合法订阅下载等同允许公开上传。第三方源、补丁和许可证须在制品中保留必要通知。

## 8.3 上线顺序

先独立测试两类应用，再预发布，最后按可回滚服务/实例灰度。每步检查 5xx、P95/P99、OOM、错误、后端连接和业务成功率。新旧共存时先确认数据库、缓存/Session 序列化和代码配置兼容。

完成时检查所有 FPM pool、Pod、旧 ReplicaSet、CLI 队列、Swoole、cron 和 mod_php 实例；只换 CLI 或单个 Deployment 不能关闭整个事件。

## 8.4 安全回滚

保留旧镜像 digest/包、运行配置、应用版本和受限证据，演练如何恢复。优先回到另一份已修复构建。必须回到未修复版本时，标记漏洞重新暴露、隔离或限制入口、获得风险批准并继续修复；不要因业务恢复就写安全完成。

本机软链接、Web upstream、systemd ExecStart 和 cron 的切换各自核验。数据格式变化可能使镜像/包回退不充分；不得自动做破坏性数据库恢复。

## 8.5 标准交付

提交 [验收报告](../templates/validation-report.md)、逐 CVE [证据清单](../examples/security-evidence.example.json)、构建和扩展锁、运行手册、部署/回滚步骤、性能数据与残余风险。原始敏感取证材料留在受控制品库，Git 仅保存脱敏结果和可追溯引用。
