## 13.2 源码编译的 nginx 平滑升级

1. **只换程序，不动配置。** 照搬 `nginx -V` 里的编译参数。在与目标机相同的 CentOS 7 容器里编译，gcc 4.8.5、glibc 2.17 都一致，再用 `ldd` 确认依赖库与旧程序相同。正则继续用系统的 PCRE（`--without-pcre2`），OpenSSL 用 3.5 LTS 静态编入。nginx 和 OpenSSL 的源码都核对了 PGP 签名。
2. **先测配置再切换。** 新程序先用 `nginx -t -c 现有配置` 测一遍。再用 [`tools/nginx_targets.py --probe`](../tools/nginx_targets.py) 从 `nginx -T` 生成"域名 × 端口"清单，用 [`tools/http_probe.sh`](../tools/http_probe.sh) 记录基线。每个目标请求首页和一个不存在的地址，后者用来检验伪静态和 404 处理。
3. **平滑升级**：`USR2` 拉起新 master，`WINCH` 让旧 worker 退出，抽查一批目标，再 `QUIT` 旧 master。抽查不一致时，对旧 master 发 `HUP`、对新 master 发 `QUIT` 即可回退。
4. **切换后**：用 [`tools/probe_compare.py`](../tools/probe_compare.py) 对比全站结果，用外部的 curl 记录每个 HTTPS 站点的 TLS 版本和 HTTP 版本，最后执行 `systemctl restart nginx`，按开机时的启动路径实测一次。
5. **兼容性**：
   - `listen ... http2` 只会出现"已弃用"警告。
   - 同一个端口上有的 server 写了 http2、有的没写，会出现 `protocol options redefined` 警告，整个端口的行为不变。
   - OpenSSL 3 默认不再提供 TLSv1 和 TLSv1.1。
   - 没有显式设置 `ssl_protocols` 的站点会改为允许 TLS 1.3。
6. **编译环境的坑**：
   - 从 Docker Hub 拉 `centos:7` 卡住，改用 `quay.io/centos/centos:centos7`。
   - 从这台 WSL 访问国内镜像源很慢，改用 `vault.centos.org`。
   - OpenSSL 3.5 的 Configure 需要 Perl 模块，装 `perl-core`（其中包含 Time::Piece）。

## 13.3 PHP 从宿主机迁到容器：设计

- **两个容器，同一个镜像**，都使用 `network_mode: host`：
  - `php72-fpm`：监听宿主机原来的地址。
  - `php72-cli`：用宿主机原有的 supervisord 配置运行队列。
- **原路径挂载**：代码、上传文件、日志、会话目录都按宿主机原路径挂载；容器里的用户 uid 与宿主机相同。这样 nginx 配置、`SCRIPT_FILENAME`、文件属主都不用改。
- **配置沿用原文件**：php.ini 和池配置用宿主机原文件的副本，剩余差异由 [`tools/ini_parity.py`](../tools/ini_parity.py) 生成补齐文件。
- **命令行照旧**：宿主机的 `/usr/bin/php` 换成转发脚本，crontab、发布脚本和手工命令都不用改。非 root 用户经过一条只放行转发脚本的 sudo 规则执行。
- **supervisord 管理方式不变**：`php72-cli` 直接读取宿主机的 `/etc/supervisord.conf`，并挂载其 socket 目录，所以 `supervisorctl`、9001 管理端口和监控脚本都照常可用。
- **/tmp 与原来一致**：
  - 宿主机上的命令行 PHP 本来就和其他程序共用 /tmp，所以 `php72-cli` 默认挂载 /tmp。
  - Remi 的 php-fpm 默认使用私有 /tmp，与容器相同；只有原来设置了 `PrivateTmp=no`（例如会话存放在 /tmp）时，`php72-fpm` 才挂载 /tmp。
- **慢日志**：FPM master 用 ptrace 读取 worker 的调用栈。池配置开了 `request_slowlog_timeout` 时，`php72-fpm` 要加 `SYS_PTRACE`。

## 13.4 实施步骤

1. **盘点（只读）**：
   - FPM 实际生效的配置：用 `kit/ini_dump.php` 配合 `kit/fcgi_get.php`，通过 FastCGI 请求导出。
   - CLI 实际生效的配置。
   - 池配置。
   - supervisord 的各个程序：运行用户、路径、`stopwaitsecs`。
   - 各用户的 crontab，以及 cron 调用的脚本。
   - 业务代码对宿主机的依赖：`exec`/`popen` 调用的命令、系统字体、sendmail（这两台都是没有配置的 ssmtp）、MySQL socket。
   - 网站根目录、docker 和 compose 的版本。
   - nginx 在容器里运行时，`nginx -T` 要带上与启动命令相同的 `-p`、`-c`。root 是相对路径时，用 `tools/nginx_targets.py --prefix` 补全。
   - php-fpm 的 `PrivateTmp`（`systemctl show php-fpm -p PrivateTmp`）、池配置的 `request_slowlog_timeout`。
   - Remi 包的来源仓库（`yum list installed 'php*'` 的第三列），回滚时要从同一个仓库下载。
   - sshd 的 `ClientAliveInterval`、`ClientAliveCountMax`：设置了空闲断开时，切换脚本必须脱离 SSH 会话执行。
2. **扩展对比**：宿主机有、镜像没有的扩展必须为 0；镜像多出的用 `PHP_DISABLE_EXT` 关闭。逐个核对关键扩展的版本，这次 redis、mongodb、swoole 的版本完全相同。
3. **配置校准**：
   1. 在本地起一个容器，挂载宿主机的 php.ini 和池配置，导出实际生效配置。
   2. 用 `tools/ini_parity.py` 对比，生成补齐文件。
   3. 带上补齐文件再导出一次，确认只剩预期差异：`extension_dir`、`opcache.max_accelerated_files`、`opcache.optimization_level`、`sqlite3.defensive`、sodium。
4. **并行验证**：用 [`kit/setup-runtime.sh`](../variants/php72-host-compat/kit/setup-runtime.sh) 在测试地址启动新 FPM，经 SSH 隧道用 [`tools/fcgi_compare.py`](../tools/fcgi_compare.py) 对比各站点入口（目标由 `tools/nginx_targets.py --fcgi` 生成）。有差异时，用同一个目标对旧环境连续请求两次：如果两次也不一样，就是动态内容（例如 SSO 跳转里的随机 token），不算迁移造成的差异。
5. **切换**：[`kit/cutover.sh`](../variants/php72-host-compat/kit/cutover.sh)，依次是：保存回滚用的 RPM → 记录基线 → 切换 FPM → 切换 supervisord → 删除 Remi PHP → 安装转发脚本 → 再次探测。每一步都先验证，出错即停。
   - 在生产主机上用 `setsid nohup bash cutover.sh > 日志 2>&1 < /dev/null &` 执行，SSH 只用来轮询日志：SSH 中途断开时，脚本不会停在一半。
   - `PROBE_PATHS` 里加上首页之外的入口（后台入口、带 `s=` 参数的路由），探测更全面。
6. **验证**：
   - 全站对比。
   - FastCGI 运行态：版本、uid、扩展、opcache。
   - root 和业务用户分别执行 `php think list`，命令数要相同。
   - 队列的 RUNNING 数和程序名与切换前一致。
   - 定时任务看 `docker events` 中 `exec_die` 的退出码。退出码不为 0 时，用 Docker API `/exec/<execID>/json` 查出具体命令，再查这个任务自己的日志，判断迁移前是否就失败。
   - 业务指标，切换前后各取一次：nginx 访问日志的请求数、5xx 数、平均耗时，PHP 错误日志的新增行数，ThinkPHP 当天 error 级日志的行数。
   - 临时的验证脚本要放在挂载目录（例如 /tmp）里：切换后 php 在容器里执行，看不到 /root。
   - 资源开销：dockerd 的 CPU。
7. **清理**：
   - 删除旧版本的安装目录和 rpmsave 文件。
   - 移除重复的 `supervisor.service`，以及指向旧路径的启动脚本。

## 13.5 踩过的坑

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | 用 `bash -s` 远程执行的脚本跑到第一个 `php` 就结束了 | `docker exec -i` 把调用方的标准输入全部读走；原生 php 不会 | 转发脚本只在交互终端下加 `-i`，需要管道输入时用 `PHP72_STDIN=1`。否则 `while read ...; do php ...; done < 文件` 也会出问题 |
| 2 | 脚本开头写了 `exec < /dev/null`，经 `bash -s` 执行时一行都没跑 | 脚本本身就是从标准输入读进来的 | 关闭标准输入的脚本必须以文件方式执行 |
| 3 | 容器里 memory_limit 是 256M、上传上限 32M、时区 Asia/Shanghai，与宿主机不同 | 基础镜像的 `99-production.ini` 覆盖了 php.ini | 在镜像里删除这个文件 |
| 4 | 差异清单里有 `msgpack.assoc`（宿主机为空，容器为 1） | 宿主机的 msgpack 2.2 **没有这个指令**，它是 3.0 新增的，默认值 1 与 2.x 行为一致 | 不能写成 Off，否则 map 会被解包成对象。`ini_parity.py` 对这种"只有新环境才有"的指令只给提示，不写入 |
| 5 | `phpdismod sodium` 报 ini 文件不存在 | sodium 编译在 Sury 的 PHP 主程序里 | 接受这个差异（只是多出一组函数） |
| 6 | 容器 FPM 里加载了 readline | Sury 对所有 SAPI 都启用了 readline | 只在 fpm 上关闭 |

| 8 | 补齐文件所在的位置变成了一个目录 | 挂载时宿主机上还没有这个文件，docker 自动建了同名目录 | 挂载前先确认文件存在 |

| 11 | `supervisorctl pid` 给出的进程号在宿主机上对不上 | 这是容器内的 PID | 用 `docker top php72-cli` 对应 |
| 12 | 每分钟有 3 次定时任务退出码为 1 | crontab 调用的 `lndx:wechat:live:sync` 在测试代码里不存在，迁移前就一直失败 | 用 `docker events` 的退出码定位，再用 `php think list` 核对 |
| 13 | 队列配置里写着 `stopwaitsecs=3600` | 允许每个进程最长花 1 小时收尾 | 实际 1 秒就停了，但切换要按最坏情况准备：`timeout 300 supervisorctl stop all`，超时后由 `systemctl stop` 强制结束 |
| 14 | `scp 主机:/路径/{a,b}` 什么也没复制 | OpenSSH 9 的 scp 默认走 SFTP，不展开远程的花括号 | 逐个文件复制 |
| 15 | 并行对比第一次全部"连接被拒绝" | SSH 隧道还没建好对比就开始了 | 等本地端口开始监听后再开始对比 |
| 16 | fail2ban 容器 11 个月没有封过 IP | 它只挂载了 `/var/log/secure` 这一个文件，日志轮转后一直在读旧文件 | 改为挂载 `/var/log` 目录 |
| 17 | `pkill -f 模式` 把执行它的命令自己也杀掉了 | 当前命令行本身也包含这个模式 | 按 PID 杀，或者把模式写成 `[x]yz` 的形式 |

## 13.6 日常维护

| 操作 | 方法 |
|---|---|
| 新增、修改、删除 supervisor 任务 | 和以前一样：编辑 `/etc/supervisord.d/*.conf`，然后 `supervisorctl reread && supervisorctl update`（已实测新增、改为 2 个进程、删除） |
| 定时任务 | 和以前一样：`crontab -e` 或 `crontab -e -u 用户`。实测新增的任务在容器里以原用户、原当前目录执行，退出码 0 |
| 修改 php.ini 或 FPM 池 | 编辑 `/data/php72-runtime/conf/` 下的文件，然后 `docker compose restart php72-fpm php72-cli`（只有 v1 的主机用 `docker-compose`，见 `/data/php72-runtime/.compose`） |
| 发布代码 | 不需要任何变化，代码目录直接挂载进容器 |

限制：
- supervisor 里只能放 PHP 程序。
- 路径必须在挂载目录之下。
- 新增运行用户要修改 `HOST_USERS`；如果这个用户的定时任务调用 php，还要修改 sudoers。
- 修改主配置 `/etc/supervisord.conf` 后要执行 `docker restart php72-cli`。

资源方面，dockerd 每分钟多出的 CPU 时间不到 1 秒，可以忽略。

## 13.7 回滚

每台大约 1 分钟：
1. `docker compose down`（或 `docker-compose down`）。
2. 用 `yum localinstall` 安装切换前保存在本地的 Remi RPM。
3. 解开配置备份包。包里有 rc.local。P2 的 `php-fpm.service.d/override.conf`（`PrivateTmp=no`）一直保留着，回滚后会话仍然存放在 /tmp。
4. 删除 sudoers 规则和转发脚本。
5. `systemctl enable --now php-fpm supervisord`。

具体命令写在每台主机的 `/data/php72-runtime/README.txt` 里。

## 13.8 生产实施记录

两台都按 13.4 的步骤执行，镜像为 `php72-host-compat` r2。每台先跑 `setup-runtime.sh` 并行验证，没有问题后再执行 `cutover.sh`，一台验证完再做下一台。

### P1（后台，使用 MongoDB 扩展）

- **盘点**：
  - 1 个 PHP 站点；nginx 在容器里以 `-p` 前缀启动，root 是相对路径。
  - 54 个队列（root）；业务用户的 crontab 有 98 行 php，其中 31 行每分钟执行；root 的 crontab 经两个脚本调用 php。
  - 会话在 `/var/lib/php/session`；FPM 使用私有 /tmp；只有 compose v2。
  - 镜像多出的 15 个扩展用 `PHP_DISABLE_EXT` 关闭。mongodb 1.16.2、redis 5.3.7、swoole 4.8.13 与宿主机相同；opcache 512M 由补齐文件带过去。
- **并行验证**：
  - FastCGI 5 个入口：3 个完全一致；2 个只差 SSO 跳转里的随机 token，旧环境连续请求两次也是这样。
  - FPM 的实际生效配置，以及 root、业务用户两种身份下命令行的实际生效配置，都只剩 13.4 第 3 步列出的预期差异。
- **切换**：FPM 中断 0.9 秒；队列 1 秒内停止，54 个在容器中 RUNNING；没有 `/usr/bin/php` 的时间 3.8 秒；保存回滚 RPM 19 个。
- **切换后**：
  - 经 nginx 的 10 条请求：8 条一致，2 条是上面的 SSO token。
  - 运行态与原来一致。`php think list` 在 root 和业务用户下都是 147 个命令。
  - 190 秒内定时任务执行 131 次，129 次退出码为 0，2 次是 #32 的既有问题。
  - 切换后 3 分钟内 1336 个请求，0 个 5xx；PHP 错误日志没有新增；ThinkPHP 当天 error 级日志仍为 0 条。

### P2（教务管理，会话存放在 /tmp）

- **盘点**：
  - 5 个 PHP 站点；27 个队列（业务用户）；root 的 crontab 有 17 行 php。
  - 会话存放在 /tmp：155 个会话文件，10 分钟内有 6 个更新过。
  - 慢日志已开启（`request_slowlog_timeout = 2`），当天有 84 条记录。
  - 加载了 dba、recode；compose v1、v2 都有。
- **并行验证**：
  - FastCGI 9 个入口全部一致。
  - 向新 FPM 发一个睡眠 3 秒的请求，慢日志里有完整的调用栈。
- **切换**：FPM 中断 2.2 秒（池要先启动 20 个 worker）；队列 1 秒内停止，27 个在容器中 RUNNING；没有 `/usr/bin/php` 的时间 5.3 秒；保存回滚 RPM 24 个。
- **切换后**：
  - 80 条请求全部一致；运行态一致；`php think list` 在 root 和业务用户下都是 42 个命令。
  - 定时任务退出码全部为 0。
  - 容器 FPM 写入的会话文件属主正确；ptrace 报错 0 次。
  - PHP 站点切换前后都没有 5xx。
  - 切换后的前 5 分钟，P95 耗时从 0.44 秒升到 0.95 秒，原因是 opcache 重新预热；之后回落到 0.09 秒。
  - `docker stats` 里 `php72-cli` 的 CPU 约为 1 核，这不是新增的负载：
    - P2 的队列用 `think queue:listen` 运行，它每处理一个任务都会新启动一个 `sh -c php think queue:work` 子进程。27 个队列 ×（listen + sh + work）再加上 supervisord 和 tini，正好是 83 个进程。
    - sar 记录的宿主机 CPU 在切换前后没有变化。
