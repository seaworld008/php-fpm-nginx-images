## 12.2 补丁状态与证据

- **Sury 7.2.34-66 / 7.4.33-31**：源码包 `debian/changelog` 有 `Backported from 8.2.35 ... [CVE-2026-109618, CVE-2026-109619]: Avoid state corruption via bailout.` 条目。只核对了 changelog，没有逐行审计补丁、也没有做针对性回归，按 [01 章](01-security-and-sources.md) 记为 `UNVERIFIED`，不作安全声明。
- **Remi EL7 `7.2.34-22.el7.remi`**：changelog 最后一条是 2024-06-04，没有任何 2025/2026 年的条目。它修复了 7.2.10～7.2.24 时期的大量旧漏洞，但**不包含 2026-10 这两个 CVE**。Remi 对 EL7 的构建已经停止，CentOS 7 上找不到带这两个补丁的 PHP 7.2 包。因此 T1、T2、P1、P2 这四台在这两个 CVE 上仍是未修复状态，需要另行决策：迁到容器并使用同一个 Sury 镜像，或者自行回移补丁重新打包。
- **Ubuntu 24.04 php8.3 `8.3.6-0ubuntu0.24.04.13`**：changelog 写明 `SECURITY UPDATE: Remote RCE via state corruption issue`，补丁文件为 `debian/patches/CVE-2026-109618_109619.patch`。同样只核对了 changelog，记为 `UNVERIFIED`。
- **CI 构建的业务镜像不会自动换基础镜像。** 复查时在测试主机上发现一个 2026-10-08 构建的业务镜像仍是 Sury `7.2.34-43`（2023-09），不含这两个补丁；同一台主机上当天重新构建的镜像已经是 `7.2.34-66`。基础镜像更新后，要逐个确认使用它的业务镜像都已重建。
- 升级时曾把 Remi 7.2.34 描述为"最新漏洞修复版"，这个说法不准确。教训：升级前先查清目标 CVE 的修复日期，再与目标包 changelog 的最后日期对照。

## 12.3 CentOS 7 宿主机升级经验

1. **先拿证据确认根因，再考虑改代码。** 测试机上 lndx 后台 500，日志是 `NOAUTH Authentication required.`。这是 **Redis** 的报错，而一度被误判为 MongoDB 认证失败，结果去改了 vendor 代码、硬编码了配置，差点推到仓库。真正的原因是新 FPM 以 `apache` 用户运行，读不到权限 640 的 `.env`，Redis 密码为空。`.env` 中密码里的 `%` 已按 URL 规则写成 `%25`，本来就正确（think-mongo 把密码拼进 URI，驱动会解码）。最终没有改任何代码。
2. **FPM 运行用户必须和旧版一致。** Remi 默认用 `apache`；OneinStack 原来是 `www`，生产两台是 `nginx`。用户不一致时 `.env` 读不到，日志、缓存、session 写不进去，测试机上有二十多个站点受影响。还要让该用户能访问 Remi 由 RPM 管理的目录：用 `usermod -aG apache <用户>` 获得 `/var/lib/php/session` 的权限，用 `setfacl` 获得 `/var/log/php-fpm` 的权限。直接改目录属主，下次 `yum update` 会被还原。用 `apache` 运行期间产生的缓存和 session 文件，要改回原属主。
3. **扩展逐个对比旧版本。** 用旧二进制加 `-c 旧php.ini -d extension_dir=...` 导出 `php -m`，再和新版本比较，"旧有新无"必须为空。测试机一度缺 9 个扩展（gd、mbstring、zip、intl、swoole、imagick 等），原因是升级脚本删掉了 `remi-safe` 源，依赖库装不上。另外要用 `rpm -qf` 确认扩展目录里的每个 `.so` 都属于某个包，不留手工编译的扩展（见 12.6 第 4 条）。
4. **不删除或覆盖已有 yum 源。** 新建一个默认禁用的源文件，升级时用 `--disablerepo='*' --enablerepo='phpup-*'` 显式启用。Remi 公钥要与官网核对指纹（`1EE0 4CCE 88A4 AE4A A29A 5DF5 004E 6F47 00F9 7F56`）。正式安装前先做 `yum --assumeno` 演练，确认不会顺带升级系统库。
5. **绝不按进程名 kill。** 宿主机能看到容器内的进程，曾误杀测试机上一个业务容器的 php-fpm 主进程（已重启容器恢复）。停服务前先检查 `/proc/<pid>/cgroup` 不含 docker，并且只通过服务管理器（systemd、rc.local 等）停止。
6. **配置照搬旧版，不用默认值，并用 `php-fpm -i` 全量对比确认**（只对比扩展会漏掉 ini，见 12.6 第 1 条）。php.ini 用旧文件，并注释掉 `extension=` 行，避免与 `php.d` 重复加载（这次顺带消除了一个多年的 `mongodb already loaded` 警告）。FPM 池参数照搬：`max_children`、`request_terminate_timeout`、慢日志、`php_admin_value`；相对路径改为绝对路径。opcache 内存照搬。`curl.cainfo` 指向的证书文件一并迁移。旧 FPM 的 session 存在 `/tmp` 时，要用 systemd drop-in 设置 `PrivateTmp=false`，否则所有用户会被踢下线。
7. **所有入口都要切换**：FPM、supervisord 队列、crontab、`/etc/profile`、rc.local 和开机自启都要改，**cron 调用的脚本内部**写死的路径也要改（见 12.6 第 2 条）。测试机的 php-fpm 一度没有设开机自启。
8. **先装后切，保留回滚。** 旧版本是编译安装（独立目录）时，新旧可以并存，切换中断不到 1 秒。旧版本是 RPM 时只能换包：先把旧 RPM 下载到本机并校验签名和版本（服务器下载太慢时，在网络更好的 WSL 下载再传过去），再用一个 `yum shell` 事务完成"删旧装新"，中断约 4 秒。
9. **切换前后用数据对比**：逐站点状态码、访问日志中的 5xx、应用 error、队列日志。
10. **测试页面和调试脚本用完即删**，尤其是会输出配置的。

## 12.4 容器主机升级经验

1. **基础镜像不能直接替换上去。** v20261022 是"nginx + FPM + supervisord"一体镜像：FPM 监听 unix socket，运行用户 `nginx`(999)，自带依赖 nginx 的健康检查。而原 `php72` 只运行 FPM，监听 `0.0.0.0:9000`，用户 `application`(1000)，并且只授予了少量 capabilities。所以派生了 FPM 专用变体：`ENTRYPOINT []`、`HEALTHCHECK NONE`、添加 uid 1000 用户、池配置照搬旧镜像。
2. **phpredis 版本（已更正）。** Sury 只提供 phpredis 6.x，变体源码编译 5.3.7，与原镜像（5.3.5）保持同一主版本，减少行为变化。此前这里写的"6.x 删除了 `Redis::delete()`，TP5.0 删缓存、退出登录会报致命错误"是错的：5.x 和 6.x 都有这个方法，而且行为相同，见 [12.9](#129-勘误)。
3. **用 `php-fpm -i` 导出全部指令做逐项对比。** 两边各导出一份 `指令 = 值`，用 `join` 比较，再逐项判断是对齐还是有意保留。这次发现的实质差异：
   - Debian 的 FPM php.ini 默认 `disable_functions = pcntl_*`，旧镜像为空：已对齐。
   - Sury 的 `memcached.serializer = igbinary`，旧值是 `php`：已对齐，否则新写入的缓存数据旧客户端读不了。
   - `max_input_vars`、`realpath_cache_ttl`、`memcached.store_retry_count`、`session.save_path` 也已对齐。
   - 有意保留：`opcache.revalidate_freq` 60→2，`opcache.max_accelerated_files` 4000→10000。
4. **webdevops 兼容**：不加载 php.ini，只用内置默认值，加上 `98-webdevops.ini` 和挂载进来的 `99-docker.ini`。Apache 配置通过 `/opt/docker/etc/httpd/main.conf` 引入，保持 vhost 的加载顺序（挂载的业务 vhost 是第一个 `*:80` 虚拟主机，即默认站点）。443/SSL 没有对外发布，未启用。旧容器里虽然运行着 cron、syslog-ng，但没有任何任务，所以没有迁移。
5. **并行验证再切换。** 新镜像用同样的挂载和安全选项，起一个只监听本机端口的测试容器，再用 `tools/fcgi_compare.py` 对新旧 FPM 发送同样的只读 GET 请求。Apache 类镜像则直接对新旧端口用 `curl` 请求访问日志里的真实页面，比较状态码和字节数。
6. **网关会缓存容器名解析出的 IP。** openresty 用 `proxy_pass http://wslndx_web1:80` 转发，nginx 启动时就把容器名解析成了 IP。重建容器后新 IP 变了，网关还在发往旧 IP。这次从旧容器被移除到执行 `openresty -t && openresty -s reload` 恢复，约 30-40 秒，期间只有一个测试请求受影响。**凡是被网关按容器名转发的容器，重建后都要立即重载网关**，或者改用 `resolver` 加变量的动态解析。网关通过宿主机 `IP:9000` 访问的 `php72` 不受影响。
7. **compose 细节**：
   - 多副本服务必须带上 `--scale 服务=N`，否则会被缩回 1 个。
   - 只重建目标服务时用 `--no-deps`。
   - 旧镜像不响应 SIGTERM 时，会等满 10 秒默认停止超时；新镜像里 FPM 是 1 号进程，会正常退出。
   - 队列重启时，处理中的任务可能被重新投递。
8. **镜像传输**：用 `docker save | gzip | ssh docker load` 直接传到目标机，没有经过镜像仓库。目标机已有的层仍会重复传输，472MB 镜像用了 82 秒。
   - 风险：仓库里没有这两个标签，目标机本地镜像丢失时 compose 无法重新拉取，需要补推。

## 12.5 诊断经验

- curl 报错 `cURL error 3: <url> malformed` 在浏览器里只显示 "malformed"，因为 `<url>` 被当成了 HTML 标签。它表示请求的 URL 为空或者是相对路径，通常是业务配置缺失（例如超级管理员没有学校 ID，取不到第三方接口地址），与 libcurl 版本无关。
- 判断一个报错是不是升级引起的：保留旧二进制，**用新旧两个 PHP 分别跑同一段代码**，结果一致就与升级无关。jxgl 的大华 URL 报错和 Java 网关超时，都是这样排除的。
- 统计日志时，时间截取一定要先在样例行上验证。这次曾因 `substr` 偏了一位，把升级前的报错算到了升级后。

## 12.6 复查发现的遗漏（2026-10-23）

升级当晚对六台主机做了一次全量复查，发现并处理了这些问题：

| # | 问题 | 怎么发现的 | 处理 |
|---|---|---|---|
| 1 | T1、T2 第一次升级只对比了扩展，php.ini 和 FPM 池参数仍是 Remi 默认值（时区、`disable_functions`、各类上限、`short_open_tag`、swoole 短名、进程数等） | 新旧 `php-fpm -i` 导出全部 `指令 = 值`，用 `join` 逐项对比 | 迁移旧 php.ini（注释掉 `extension=` 行）和池参数后再对比，只剩两项有意保留的差异：`mysqli.allow_local_infile` 关闭、`imagick.skip_version_check` |
| 2 | P2 上有 3 个 cron 调用的脚本写死了旧路径 `/usr/local/php/bin/php`（每分钟的订单取消、晚间签到、每日同步）。切换后它们静默失败了约 3.5 小时，因为输出都重定向到了 `/dev/null` | 从 crontab、supervisor、rc.local 中提取被调用的脚本，再 grep 旧路径；同时 grep 应用代码里写死的 PHP 路径（未发现） | 备份后改为 `/usr/bin/php`，手动执行一次订单取消任务，rc=0。签到任务按"当天日期"处理数据，过了零点不能直接补跑，漏跑的数据交业务确认 |
| 3 | 容器主机 C 的宿主机上还装着 Ubuntu 的 php8.3（FPM 未启用，只有 CLI），版本不含这两个 CVE 的补丁 | `dpkg -l 'php*'` 和 changelog | `apt-get update` 后只升级 php8.3 的 13 个包到 `.13`。升级前先用 `apt-get -s` 演练，确认不会带上其他包 |
| 4 | T1 上有一个排查期间手工编译的 mongodb 1.9.2，不属于任何 RPM，版本也与生产 P1（Remi 1.16.2）不同 | 对扩展目录里每个 `.so` 执行 `rpm -qf` | 换成 Remi `php-pecl-mongodb` 1.16.2。切换前后都用应用自己的配置向 MongoDB 发 `ping`，都返回 `ok:1`；页面状态码和字节数没有变化 |
| 5 | T1 上一个由 CI 构建的业务镜像仍是 2023 年的 Sury 7.2.34-43 | 对每个运行 FPM 的容器做运行态探针（见下） | 需要在 CI 里改基础镜像后重新构建，待业务方处理 |
| 6 | 早期的一个自动升级脚本卡在确认提示上 5.5 小时。脚本文件已被删除，但进程还在等输入，一旦误输入确认，就会按旧方案重新执行 | 检查本机的后台任务 | 停掉该进程，并清理本机的临时密码文件 |

**运行态探针。** 用 PHP CLI 写一个最小的 FastCGI 客户端，把一个只输出 `phpversion()`、扩展版本和 `opcache_get_status()` 的脚本放到 `/dev/shm`（容器里放 `/tmp`），直接请求本机或容器内的 FPM，用完就删。这样不用改网站目录，也不经过 Nginx。上面第 5 条就是这样发现的，各 FPM 的实际运行用户、opcache 命中率和内存余量也是这样确认的：P1、P2 的命中率为 97%～100%，没有 oom 或 hash restart。

**对齐前先确认旧版本是否真的启用了。** P2 的旧 php.ini 里写了 `opcache.memory_consumption=512`，但没有 `zend_extension`，旧 `php -m` 里也没有 OPcache，说明旧版本根本没开 opcache，也就谈不上"对齐 512M"。新版本默认开启 128M，当前用了约 30M。

## 12.7 入侵排查（只读）

每台主机按同一份清单执行，全程只读：

1. **账号**：UID 0 的账号；可登录账号及其密码状态（`passwd -S`）和最后改密日期；sudoers；`passwd`、`shadow` 的修改时间。修改时间与 RPM 安装新建系统账号的时间对得上，就属于正常。
2. **SSH**：各账号 `authorized_keys` 的数量、修改时间和注释；sshd 配置；所有保留日志中成功登录的"来源 × 用户 × 方式"统计；wtmp 里每个公网来源的最近一次登录。再把公钥登录日志里的指纹与 `ssh-keygen -lf authorized_keys` 对照，确认用的是哪把钥匙，比如发布系统的钥匙。
3. **持久化**：`/etc/ld.so.preload`；cron，包括 cron 调用的脚本；近 30 天新增或修改的 systemd 单元；rc.local；profile.d。
4. **进程与网络**：CPU 占用前几名；常见挖矿进程名和矿池端口；从临时目录或已删除文件运行的进程；与非内网地址的已建立连接（按进程和本地端口聚合）；监听端口。
5. **临时目录**：`/tmp`、`/var/tmp`、`/dev/shm` 中的可执行文件和隐藏目录。
6. **网站目录**：把 Nginx 的 `root`、容器的 bind mount 和常见路径汇总成目录列表，去掉嵌套目录后，对 `*.php`、`*.phtml`、`*.inc` 做 webshell 特征扫描，**记录每个目录的文件数、耗时和是否超时**：超时就等于没扫。另外检查 `.user.ini`、`.htaccess` 中的预加载和处理器改写，以及上传目录、静态目录里的 PHP 文件。
7. **系统命令完整性**：`rpm -V` 或 `dpkg --verify` 中摘要发生变化的可执行文件。
8. **容器**：特权、宿主网络、宿主 PID；近 7 天创建的容器及其镜像。

**判断大批量文件改动的来源**：先按"一级目录 + 修改小时"聚合，再用 `debugfs -R 'stat <inode>' <设备>` 读取 inode 的创建时间 crtime。这次 P2 上两万多个文件的 mtime 是 22:07:25，crtime 却是 22:08:41，说明这些文件是 22:08 由解包工具新建的，解包时保留了原来的 mtime。再对照 22:08:16 的一次公钥登录，那把钥匙的注释是发布系统，所以这是一次正常发版。

**结论（截至 2026-10-23）**：六台主机都没有发现入侵迹象。

- UID 0 只有 root，公钥都能对应到已知用途，成功登录的来源都是内网、办公出口或发布系统。
- 没有 `ld.so.preload`、可疑 cron、挖矿进程或矿池连接。
- webshell 扫描全部跑完，没有命中。最大的目录约 95 万个文件，扫描用了 6 分钟。
- `rpm -V`、`dpkg --verify` 都没有异常，大批量的文件改动都能对应到发版。

**局限**：认证日志只保留了约 5 周；没有文件完整性基线（例如 AIDE）；特征扫描发现不了经过混淆的后门，也查不到只驻留在内存里的后门。所以结论是"没有发现"，不是"证明没有"。

## 12.8 加固建议

排查时还看到一些与这次升级无关的加固项，涉及 SSH 认证方式、对外暴露的端口、特权容器和更新后长期未重启的服务等。这些已在内部报告中逐台列出，**不在公开仓库中记录细节**。通用做法：

- SSH 只放行办公出口和跳板机，改为仅密钥登录，并确认 fail2ban 的实际封禁记录。
- 数据库、rsync、内网穿透等端口用安全组限制来源；不用的守护进程停掉。
- 系统包更新后，用 `needrestart` 或 `/proc/*/exe` 中的 `(deleted)` 找出仍在运行旧二进制的进程，在维护窗口内重启。
- 应用日志目录（例如 ThinkPHP 的 `runtime/log`）要设置清理策略。

## 12.9 勘误

- **phpredis 与 `Redis::delete()`**（影响 12.4 第 2 条、变体 README 和 CHANGELOG 中的旧说法）。实测结果：
  - phpredis 5.3.4、5.3.5（两个原镜像）、5.3.7（变体）、6.0.2（`v20261022`）、6.3.0（7.4 变体）都有 `Redis::delete()`，都标记为 deprecated，每次调用都会产生 `E_DEPRECATED`。
  - ThinkPHP 5.0.24 的 `Error::register()` 设置了 `error_reporting(E_ALL)`，`appError()` 会把这个级别的错误抛成异常。连真实 Redis 测试，TP 5.0.24 的 Redis 缓存 `rm()` 在 5.3.7 和 6.0.2 上都抛出 `think\exception\ErrorException: Function Redis::delete() is deprecated`。
  - 所以这是 TP 5.0 + phpredis ≥ 5 的既有问题，新旧镜像行为相同，不是升级引入的，也与 phpredis 主版本无关。使用 Redis 缓存或 Redis Session 的 TP 5.0 项目，应在应用里把驱动中的 `delete()` 改为 `del()`。
  - 检查方法：`(new ReflectionMethod('Redis', 'delete'))->isDeprecated()`，并用 `set_error_handler` 捕获调用时的 errno（8192）。
- **仓库根目录的总结类文档**（`FINAL_SUMMARY.md`、`PROJECT_SUMMARY.md`、`PRODUCTION_EXPERIENCE.md`、`IMPLEMENTATION_SUMMARY.md`、`QUICK_REFERENCE.md`、`START_HERE.md`、`GITHUB_RELEASE_GUIDE.md`、`PR_BODY.md`、`PR_DESCRIPTION.md`、`RELEASE_NOTES_v20261022.md`）中，"CVE 已修复 / 验证通过 / 补丁生效"等说法证据不足：Sury 只有 changelog 条目，补丁没有审计，也没有做针对性回归，状态以 `UNVERIFIED` 为准。
- **`v20261022` 镜像的实测组件**（2026-10-23，镜像 465MB）：nginx 1.30.6，PHP `7.2.34-66+0~20261021.122+debian12~1.gbpe0bcd4`，phpredis 6.0.2，mongodb 1.16.2，swoole 4.8.13。`RELEASE_NOTES_v20261022.md` 中写的 nginx 1.26.2、redis 5.3.7、mongodb 1.19.4 与实测不符。
